# Auto Drive, Launch Lab, and 3D Highway

## Goal

Start with **Auto Drive**, an opt-in simulator mode for every playable car. Let the player leave the accelerator down hands-free while the car automatically lifts and brakes for traffic, follows a lead car, and returns to full throttle when the lane clears. Deliver the first playable version in Live Drive, then build **Launch Lab** for repeatable launches and **3D Highway** for manual driving, Auto Drive and comparisons of documented factory driver assistance. Complete, verify, and open a draft pull request for Auto Drive before starting Launch Lab or 3D Highway. Work through routine issues independently and report specific blockers with the relevant evidence.

## Milestone 1 · Auto Drive in Live Drive

1. Add an iPad-friendly **Auto Drive** toggle to Live Drive. It starts off and works with every playable configuration using the active car and tuning. Explain in the UI that this is a simulator aid for accelerator and brake. Keep the existing gear-shift controls and drivetrain behavior. The feature should be playable using the existing road display with visible traffic and HUD feedback before any 3D work. When Highway becomes available, reuse the same controller there.
2. With Auto Drive active and the lane clear, request **100% throttle** through the normal pedal smoothing and drivetrain path. Keep each car's modeled traction, torque, shift and speed limits. When closing on a lead car, lift early enough to account for closing speed, then brake as needed and settle near a **2-second following gap**, with a minimum standstill gap. Ease back onto the throttle when the lead pulls away or changes lanes, reaching 100% when clear. Tune for smooth transitions and leave enough hysteresis to avoid cycling between accelerator and brake. The gap and response are simulator defaults shared across cars.
3. Generate light traffic using a seed and simulation time. Start with encounters roughly every **12–25 seconds** while driving and traffic speeds around **75–125 km/h**, with occasional lane changes both into and out of the player's lane. In Live Drive, the player can stay in a fixed lane. Show adjacent traffic and in-lane traffic clearly, track the nearest lead in the player lane, and make adjacent traffic start affecting the controller when it cuts in. Spawn vehicles with workable separation for the simulated closing speed. Replaying a seed with the same initial state and inputs should reproduce the encounter sequence and controller behavior. Offer a repeatable cut-in for testing as well as free driving with sparse traffic.
4. Use a small reusable traffic and longitudinal-control module, updated on simulation time. Feed the winning throttle and brake commands through `useDriveSimulation.ts` to `VehicleSimulator`. Give driver brake input immediate priority and cancel Auto Drive. Give the player an explicit toggle-off action and require deliberate re-engagement after reset, car change, view exit or loss of focus. Clear stale input on disengagement so automatic throttle cannot carry over. Resolve Auto Hold when the controller starts or resumes motion. Show Auto Drive status, current lead speed and distance or time gap, and whether it is accelerating, following or braking. Keep manual Live Drive and the stock test paths working as before.
5. Verify clear lane at 100% requested throttle, gradual closing on a slower lead, a cut-in, a cut-out and return to full throttle, manual brake cancellation, and deterministic playback. Check that the feature works on the owner's Lexus IS 200t, the owner's Škoda Superb, and one playable hypercar such as the Rimac Nevera. The Škoda's catalog entry remains `acc: false`; the Lexus's ACC stays unspecified. Factory ACC metadata must neither gate Auto Drive nor be inferred from it. Verify that the mobile controls make the behavior easy to start, observe and cancel.

## Milestone 2 · Launch Lab

1. Add a reachable Launch Lab using the active playable car and its selected tuning. Reuse the live pedals and paddles for a timed standing start. Let the player stage the car, choose how to apply throttle, and brake-boost where the existing drivetrain model supports it. Use existing automatic and manual shift behavior. Expose adjustable launch settings only where the underlying model supports the adjustment. Use the existing metrics code for 60 ft, 0–100 km/h and quarter-mile results where completed.
2. Offer **Fixed Conditions** for repeatable practice and **Variable Conditions** for visibly changing launches. Start with dry and damp surfaces, an estimated temperature-to-grip response by generic tire compound, and simple warm-up and cool-down dynamics. Let the player see starting tire temperature before the launch and choose a short cooldown or an immediate retry in the variable session. Change results through the simulated states and inputs. Give a variable-condition run a reproducible starting-state snapshot and a seed for scenario generation. Replaying the same initial state and fixed-step inputs must reproduce the same result.
3. `src/tuning/buildSimVehicle.ts` already derives `tireMu` from the compound in `src/data/tires.ts`, tire width, and the car's calibrated `gripScale`. Apply the experimental surface and temperature modifiers to that resolved baseline through the existing traction and braking paths in `simulator.ts` and `forces.ts`. Keep estimates bounded and documented. During brake hold, the parked car should stay parked and torque-converter or launch-clutch slip should never count as tire slip. The current model clamps force and derives wheel speed from road speed. Show effective grip and traction-limited time or a force-demand-over-grip indicator. Label any derived proxy as an estimate. A physical slip ratio requires a separate wheel-rotation model and validation.
4. End each run with a short explanation grounded in the telemetry, such as lower initial grip or more time at the traction limit. Allow an immediate retry with the same setup and show a previous or best run as a ghost for the same car, tuning and fixed conditions. Use sampled time and distance for the ghost, following the existing `TraceSample` and `sampleAt` pattern. The existing saved-results format retains only time and speed, so give the ghost its own session trace or add backward-compatible optional data if persisting it. Clearly label comparisons made across differing conditions.
5. Include a three-run consistency challenge with average 0–100 and spread, or an equivalent short session that makes cooldown and launch choices matter. Verify with the RWD Lexus and AWD Škoda, and sanity-check an existing playable hypercar. Demo both repeatability with the same inputs and a traction-limited case where conditions alter the output. Keep intake heat soak, tire pressure, water depth, and grade as follow-ups after this loop is playable.

## Milestone 3 · 3D Highway

1. Add a separate, lazy-loaded Highway view. Start with one short 3D loop, a cockpit or bumper camera, lane markings, steering, and traffic. Use lightweight geometry and client-side assets. Reuse the current longitudinal drivetrain and its fixed-step interface. Add road-relative lane position, heading, lateral motion, and traffic simulation as a separate layer. Use a simple, documented lateral model and keep rendering independent of simulation time. Preserve desktop keyboard and iPad touch controls, including simultaneous steering and pedals and input release on blur or pointer cancellation. If a 3D renderer is needed, choose a small dependency and document the choice.
2. Make manual driving playable with three restartable scenarios: a lead-car cut-in, a stop-and-go queue, and a curve with degraded lane markings. Use fixed or seeded traffic scripts so replaying a scenario with another car presents the same setup. Reuse Auto Drive for the player's longitudinal controls and keep steering with the player in that mode. Add a HUD for the current mode, target speed where applicable, gap, tracked lead vehicle, detected lanes and takeover prompts. A cut-in should expose the change in gap, response onset and braking smoothness.
3. Offer **Factory Assist** as a separate driving option. Add trim-, year- and market-specific assistance metadata alongside `CatalogEntry` in `src/data/catalog/types.ts`, using the existing source and confidence conventions. Support configuration-specific ACC, gap adjustment, stop/resume behavior and operating limits, lane centering, lane loss, and driver overrides. Distinguish brief lane-departure corrections from sustained lane centering. Allow longitudinal and lateral assistance together where documented. Treat assisted lane changes and driver-monitoring behavior as capability-specific additions. Brand names, a broad trim label or the presence of ACC alone do not establish combined assistance. Use one exact, source-backed playable configuration for the first demonstration if available, and label controller tuning as simulated wherever response parameters are estimated. If sources are inaccessible, deliver manual traffic and universal Auto Drive, then log the exact trims and evidence still needed for Factory Assist.
4. Route assistance commands into normal simulated throttle, braking and steering so the player can see and override them. Give throttle and brake authority to just one active mode at a time. Test brake cancellation, steering takeover, loss of the tracked target or lane, engagement boundaries, and stop/resume behavior for each implemented profile. Expose a replay button that reloads the same scenario with another supported car.
